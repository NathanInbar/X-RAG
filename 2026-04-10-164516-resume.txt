● Experiment Methodology

  Goal

  Determine which Bedrock model produces the best knowledge graph triples
  (subject-predicate-object) from academic text, to inform model selection for
  the LeanRAG production pipeline.

  Data Preparation

  1. Sample 10 documents randomly (seed=42) from the OURS dataset (academic
  papers)
  2. Segment each document into chunks using the SaT (Segment Any Text) model
  3. Filter out chunks with fewer than 20 tokens
  4. Each chunk gets a deterministic ID for cross-model comparison

  Extraction Phase

  Each of the 6 candidate models receives the same chunks and the same DSPy
  prompt (_ExtractTriples) asking it to return a JSON array of {subject, 
  predicate, object} triples. Calls are parallelized (max 4 concurrent) with
  exponential backoff retry (up to 5 attempts).

  Evaluation Phase (4 independent metric categories)

  1. Embedding Similarity (Titan v2)
  - Embed every extracted triple as a string and every source sentence
  - Topical alignment: for each triple, find its max cosine similarity to any
  source sentence, then average. Answers: "Are the triples grounded in the 
  source?"
  - Topical coverage: for each source sentence, find its max cosine similarity
  to any triple, then average. Answers: "Did the triples capture everything 
  important?"

  2. Keyword Overlap (YAKE)
  - Extract top-30 keywords from the source text using YAKE
  - Measure what fraction of those keywords appear in the triple subject/object
  fields
  - Answers: "Are key entities being captured?"

  3. Structural Heuristics
  - Redundancy ratio: fraction of triples that are near-duplicates (Jaccard
  similarity > 0.8)
  - Mean field lengths: average token count for subject, predicate, and object
  fields — detects overly verbose or trivially short triples

  4. LLM-as-Judge (Opus 4.5)
  - A judge model scores each model's output on 4 dimensions (1-10 each):
    - Faithfulness — are triples factually supported by the source?
    - Completeness — do they capture all important facts?
    - Granularity — appropriate level of detail?
    - Well-formedness — clean, unambiguous structure?
  - The judge sees only the source text + triples, not which model produced them

  Aggregation

  Two rounds of aggregation:

  1. Per-model: mean/stdev of all metrics across all chunks each model processed
  2. Intersection-based (the key fairness mechanism): find the set of chunks
  where every model successfully produced triples, then recompute aggregates
  over only those chunks. This eliminates selection bias — e.g., if one model
  fails on hard chunks, its scores shouldn't be inflated by only having easy
  chunks in its average.

  Output

  A summary table sorted by judge faithfulness, plus a detailed JSON with
  per-chunk results for deeper analysis.

  Known Limitation

  Opus 4.5 is both a candidate and the judge, which introduces potential
  self-preference bias. The code acknowledges this but mitigates it by keeping
  the judge blind to which model produced the triples.
